# 简历评估

`collect-resumes` 的下游：对当天新归档的简历逐份做 AI 筛选评估。

## 配置

| 项 | 值 |
|---|---|
| 归档根目录 | `<PROJECT_ROOT>/data/在招岗位候选人管理` |
| 评估结果输出 | 项目根 `notes/`（写 `notes/简历评估_{M.DD}.md`） |
| 评估要点文件 | 各岗位文件夹根的 `评估要点.md`（和 JD 同目录） |
| 文本提取 | `scripts/extract_text.py`（分析用：输出 JSON 带 `is_valid` 质检 + `--recovery` 多栏挽救） |

> 归档目录结构、命名、档位子目录——见 `collect-resumes/references/archive-contract.md`（单一真相源，此处不重述）。

---

## 最高优先级约束：行动加速原则

> **报告的每一部分都必须服务于 HR 的一个具体行动决策。读者看完任何一个章节，都知道"下一步做什么"。**

6 条硬约束（HR 阅读动线 + 完整格式见 `references/output-template.md`，**产出时必读**）：
1. **总览表是第一屏**——全岗位×全员一览，**必须有「工作室/团队」列**让 HR 按业务方聚类
2. **报告按「工作室→团队→岗位」三级嵌套**——岗位不能扁平排列，HR 要按归属团队拆分发；岗位排序按"强推人数优先"
3. **强推=可直接转发**——亮点精练到复制即发，附风险+面试重点+强推三道关结论
4. **可推=值得花时间面试**——说清为什么值得面、顾虑在哪
5. **待定=明确的Action**——不是"建议复核"，而是"你需要做X才能定"；Action 清单也要有「工作室/团队」列
6. **不推=一句话淘汰理由**——每个事实可溯源到简历原文

---

## 核心原则（建立判断基调）

**这个 skill 的首要价值是为面试做高效资源分配 + 不漏掉有潜力的人，不是"精确判断匹配度"。**

两条铁律贯穿全程（完整判定落档规则见 `references/analyze-prompt.md`，**每次分析必读**）：

1. **不推是重判，必须经得起复核。** 🔴不推 = 直接淘汰，风险最高。不推理由里的**每个事实**必须能在简历原文指出来。外部信号（BOSS 届数/经验）和简历事实打架 → 标"存疑"落待定，不挑一个当真。
2. **拿不准就落待定，别硬给档位。** 方向偏但有任一对口信号、深度文本不可判、外部信号冲突——这三种强制落待定 + 标"建议人工复核"。

## 阶段1：定位简历（默认今天）

> 阶段1+3 已合并为一条命令（`collect_and_extract.py`），见阶段3。此处只说明「先确认有货再跑」的判断：
> - 直接跑阶段3 的 `collect_and_extract.py --date <M.DD>`，脚本扫描不到 `{date}_*份` 目录会报「❌ 未找到」退出。
> - 没有新简历就告诉用户，结束。
> - **作品集**（文件名含"作品集""portfolio"的独立文件）脚本自动跳过，只提取简历本体；含简历的打包件（zip/rar）脚本自动解压，不会整包跳过。

> **⛔ zip/rar 包必须解压检查内部简历（2026-08-06 铁律）**
>
> 教训：8.05 赵一博的简历 PDF 打包在 zip 里（和特效 mp4 作品一起），手动列文件时把整个 zip 当"作品集"跳过，导致评估报告完全漏了他。
>
> **规则**：遇到 `.zip/.rar` 文件，**不能整包跳过**。阶段3 的 `collect_and_extract.py` 会自动解压并找包内简历（文件名含"简历/resume"优先），无需手动列内容；此处只强调判断原则：
> 1. 包内有简历 → 由 collect_and_extract 提取简历文本（包内作品 mp4/jpg 不评）
> 2. 包内无简历（纯作品集）→ collect_and_extract 会标记"纯作品集，无简历"，进兜底区
>
> "作品集跳过"只适用于**独立的**作品集文件（如 `xxx_作品集.pdf`），不适用于**含简历的打包件**（如 `xxx_简历加作品.zip`）。

## 阶段2：取评估要点

每个有简历的岗位，查其文件夹根的 `评估要点.md`：
- **有** → 直接读来评
- **没有** → 读 JD 起草草稿（5 小标题：真实看重什么/硬卡项/可放宽项/雷区/秒推信号），输出给用户确认，**阻塞等确认**后落盘。起草一次性，落盘后只读不覆盖。

## 阶段3：批量提取文本（脚本化，不手列清单）

> **⛔ 用 `collect_and_extract.py` 一键扫描+提取（2026-08-06 铁律）**
>
> 教训：8.05 手动列文件清单时漏了 zip 包内简历（赵一博），评估报告缺人。根因是"人列清单"没有兜底——脚本扫到什么提取什么，不靠人判断"这个 zip 要不要解"。
>
> **一条命令完成 阶段1+3（扫描+解压+提取+清点）**：

```bash
python "…/analyze-resumes/scripts/collect_and_extract.py" \
  --date 8.05 --output-dir notes/_extract_8.05
```

脚本自动完成：
1. 扫描归档根下所有 `{date}_*份` 目录（含档位子目录 强推/可推/待定·不推）
2. PDF/DOCX → 直接提取文本 + 质检（is_valid）
3. ZIP/RAR → **解压找包内简历**（文件名含"简历/resume"优先），提取简历文本（不会整包跳过）
4. 图片型（JPG/PNG 或 is_valid=false 的 PDF）→ 标记"图片型，需人工看原件"，进兜底区
5. 纯作品集（zip 内无简历文件）→ 标记"纯作品集"，不提取
6. **BOSS 加密文本层 PDF**（2026-08-10 新增）：BOSS 直聘把 PDF 文本层替换成 hex token（如 `45e9a67e...~~`），`get_text()` 提取出的是乱码不是文字，但渲染层正常显示。`extract_text.py` 检测到 token 行占比 >60% 时自动判定为 BOSS 加密，**渲染页面为图片**（200dpi PNG），在 JSON 里返回 `render_pages: [路径...]`。主会话用视觉模型读图片内容 → 等效于"擦掉文本层看图像"，绕过 BOSS 反爬。

**输出**：每个候选人的文本 JSON（到 `--output-dir`）+ stdout 清单表（姓名/工作室/岗位/状态/文本长度/来源）。

**拿到清单后直接读 JSON 进阶段4分析**。清单里的"图片型"和"纯作品集"进兜底区，不硬分析。
脚本已内置人数清点（输出汇总行），不需要手动交叉比对。
单份简历需要 `--recovery`（多栏挽救）时，对那一份单独跑 `extract_text.py --recovery`。
**BOSS 加密 PDF 需单独处理**：collect_and_extract 会自动渲染图片并返回 `render_pages`，但**视觉识别要主会话做**（脚本环境无 MCP 视觉工具）。主会话拿到 render_pages 路径后，用视觉模型逐页读取内容，手动写回 JSON 的 text 字段。

## 阶段4：逐份分析（主会话直接做，不派 agent）

**主会话自己读文本 + 评估要点 + analyze-prompt 模板，逐份判断。不派 sub-agent。**（日常一批就几份到十几份，上下文完全够用；agent 无上下文、倾向硬给确定档位，又慢又易错。）

读 `references/analyze-prompt.md`，按其维度和落档规则分析。每次必读，不凭记忆。

## 阶段5：产出报告（六部分）

按 `references/output-template.md` 组装（**产出时必读**，含完整六部分模板 + 档位 emoji 表 + 岗位排序规则 + 特殊情况处理 + 分发规则），写入 `notes/简历评估_{M.DD}.md` 并展示。六部分：

1. **总览**（第一屏）：全员表（含「工作室/团队」列）+ 按工作室分布统计
2. **按工作室/团队/岗位三级嵌套**的详细分析（**岗位排序按强推人数优先**）
3. **推荐摘要**（按工作室分组，可转发）
4. **待定 Action 清单**（含「工作室/团队」列）
5. **需人工看原文件**兜底区

## 阶段6：按档位分发（评估后必做）

把简历按判定 `mv` 进日期目录下的档位子文件夹（标准三档名见 archive-contract.md）：

```
已收集简历/{M.DD}_{N}份/
├── 强推/  ← 可直接打包发业务
├── 可推/
└── 待定·不推/  ← 兜底区文本异常的也放这，标注"需人工看原件"
```

分发后跑 `verify_archive.py` 确认份数没丢（闸门已兼容档位子目录，递归计数）。告诉用户各档人数。

## 阶段7：发布飞书文档（评估后必做）

> **第一性原则**：报告躺在 `notes/` 里不算完成——只有到达 HR 屏幕才算闭环。阶段6 分发完本地档位后，**自动**进入阶段7，不等用户问。

流程（3 步）：
1. **预处理**：从 `notes/简历评估_{M.DD}.md` 派生 `notes/_发布版_简历评估_{M.DD}.md`，剔除本地路径、归档说明等噪音
2. **导入飞书 Docx**：`lark-cli drive +import --file "./_发布版_简历评估_{M.DD}.md" --type docx --name "简历评估 {M.DD} · {N}人"`（飞书服务端转换器渲染 GFM 表格最稳）
3. **发链接给吴春波**：`lark-cli im +messages-send --user-id YOUR_OPEN_ID --text "{url}"`（纯 URL 飞书自动渲染卡片，AGENTS.md 飞书铁律第1条）

鉴权检查、命令模板、返回字段、失败兜底见 `references/publish-lark-doc.md`（**发布时必读**）。

完成后告诉用户：飞书文档链接 + 本地 md 路径。

## 反模式

> 判断类反模式（沉默信号/外部信号/百分比评分/自我标榜/四维度堆砌）见 `references/analyze-prompt.md`（每次必读）。下面只列 skill 执行层独有的：

- **不要自写提取脚本** — 用 `scripts/collect_and_extract.py` 一条命令扫描+解压+提取（阶段1+3 合并）。`scripts/extract_text.py` 只用于单份简历的 `--recovery` 挽救或 BOSS 加密 PDF 的单独渲染，不用于批量循环。注意：`collect-resumes/scripts/content_extractors.py` 是**归档闸门用**的提取器（关注能否验证姓名/薪酬），职责不同，两者 DOCX 库不同（分析用 fitz / 闸门用 python-docx）是有意为之。
- **不要评估完不分发** — 阶段6必做，用户要的是"能直接打包发业务"的档位文件夹。
- **不要跳过阶段7** — 评估完不发飞书=没完成。用户要的是"在飞书里看到报告"，不是"notes/ 里多一个 md"。
- **不要碰薪资** — BOSS 收简历时已按薪酬期望筛过。
- **不要平铺式输出** — 总览表是第一屏，不是按收到顺序逐个罗列。
- **不要同岗位多人无对比** — 业务一定问"帮我排个序""有什么区别"，必须答。
- **不要待定判据模糊** — "建议复核"是废话，必须写"差什么信息、看什么就能定"。
