# 产出格式模板

> **第一性原则**：报告的每一部分都必须服务于 HR 的一个具体行动决策。
> 读者看完任何一个章节，都知道"下一步做什么"。
>
> **结构原则**：报告按「**工作室/业务方 → 团队 → 岗位**」三级嵌套组织。业务方拿到报告第一眼能按归属团队拆分发，不需要自己重组。

评估结果输出到 `notes/简历评估_{M.DD}.md`，同时在终端展示。

HR 的真实阅读动线（报告必须适配这条动线）：
1. **第1秒**：扫总览——今天整体什么情况？有强推的吗？强推集中在哪个工作室？
2. **第1分钟**：翻到自己工作室的岗位章节——看强推亮点，能直接转发给业务吗？
3. **第3分钟**：扫可推——这几个值不值得安排面试？
4. **有空时**：扫待定——这几个我需要做什么才能定？
5. **几乎不看**：不推的人（一句话理由即可）

---

## 报告结构（六部分，严格按此顺序）

### 第一部分：总览（第一屏，最重要）

**一张表覆盖当天所有候选人**。表格新增「工作室/团队」列——让 HR 扫一眼能看出强推主要集中在哪个业务方。

表格按"判定档位优先 → 同档按工作室聚类"双重排序：

```markdown
# 简历评估 · {M.DD} · {N}人

> 评估时间窗：{起始时间} ~ {结束时间}。{一句话说明特殊情况：换岗/岗位调整/跨天补归档等}

## 总览

| 姓名 | 工作室/团队 | 岗位 | 判定 | 一句话理由 |
|------|------------|------|------|-----------|
| 谢荣耀 | Magnolia | AI产品经理（UGC游戏平台） | 🟢强推 | Xmind AI 0到1+网易UGC编辑器+BUD海外3DUGC，全岗匹配 |
| 黄雷 | Magnolia | AI产品经理（UGC游戏平台） | 🟢强推 | FreeFire海外UGC+雷神产品负责人+AI coding作品 |
| 彭文海 | 长青/美术 | 游戏地编设计师 | 🟢强推 | 《卡拉彼丘》新地图负责人+黑桐zplan 4年地编 |
| ... | ... | ... | ... | ... |

**{强推N} 🟢 · {可推N} 🟡 · {待定N} ⚪ · {不推N} 🔴 · {已评估N} — · 共 {N} 人**

**按工作室/团队分布**：
- **{工作室1}**（{人数}人）：{岗位1} {x} 🟢 / {岗位2} {x} ⚪ / ...
- **{工作室2}**（{人数}人）：...
- ...

> {特殊说明：岗位调整/挪岗/换岗等放在总览后单独 blockquote}
```

**表格规则**：
- 一句话理由 ≤ 25 字，只放最关键的亮点或顾虑
- 待定/不推也要在表里，不能藏在后面
- 表格下面一行汇总各档人数
- **按工作室/团队分布**是新增的"导航地图"——让 HR 第一眼看到强推的归属团队，方便拆分发
- 「工作室/团队」列用简写（如 `长青/美术`、`迷你世界/商业化`、`Magnolia`），避免过长撑爆表格

---

### 第二部分：按工作室/业务方分组的详细分析（核心）

**三级嵌套**：`# 工作室` → `## 团队（可选）` → `### 岗位` → `#### 候选人`。

#### 工作室层级（一级标题）

```markdown
---

# 第{n}部分 · {工作室/业务方名称}

{工作室简介，1-2句}本次共评估 {N} 人，{M} 个岗位。{一句关键结论：强推集中在哪/有什么亮点}
```

#### 团队层级（可选二级标题）

**什么时候加团队层**：
- 迷你世界项目团队下有「商业化运营团队」「用户和生态运营团队」——加
- Magnolia 项目团队直接是岗位扁平——不加
- 长青工作室下有「美术端」「技术端」——加（按职能分组也是团队层）

```markdown
## 美术端  // 或 ## 商业化运营团队

{团队简介（可选），通常省略}
```

#### 岗位层级（二级或三级标题，取决于有没有团队层）

**岗位排序规则**：**按强推人数优先**（强推多的岗排前），同强推数按可推数，再按岗位总人数。

```markdown
### {岗位名} — {N}人 · {档位emoji串}

> {特殊说明（可选）：岗位调整/挪岗/历史评估补充等}

#### {姓名} {判定emoji}
{2-3句综合判断：这个人水平如何、为什么这个档位、最关键的亮点或顾虑是什么}

**亮点**：{分点，只写对这个岗位真正重要的信号}
**顾虑**：{分点，诚实标注影响档位的问题}
**面试要问**：{1-2个"简历解不开的疑问"转化为面试问题}
```

**档位 emoji 串**：岗位名后加 · 跟档位 emoji，如 `— 2人 · 🟢🟢` 或 `— 3人 · 🟢⚪🔴`，让 HR 一眼看出该岗位的档位分布。

**篇幅按档位分配（信息密度不对称）**：

| 档位 | 篇幅 | 核心信息需求 |
|------|------|-------------|
| 🟢强推 | 详细 | 亮点精练到可转发 + 诚实风险 + 面试重点 + **强推三道关结论** |
| 🟡可推 | 中等 | 为什么值得面 + 顾虑在哪 |
| ⚪待定 | 精准 | **差什么信息才能定？你需要做什么？**（Action导向） |
| 🔴不推 | 一句 | 淘汰理由（每个事实可溯源到简历原文） |

**强推档必加"强推三道关"结论**（参考 analyze-prompt.md）：

```markdown
> **强推三道关**：①角色匹配——{一句话} ✓/✗ ②业务敢用——{一句话} ✓/✗ ③团队接得住——{一句话} ✓/✗
```

任一关存疑 → 降🟡可推，并在顾虑里写明是哪道关、什么疑点。

**同岗位横向对比**（2人以上时必加，放在岗位小节末尾）：

```markdown
> **{岗位}排序**：{A} > {B}。{A偏什么风格，B偏什么风格，业务先见谁}。
```

业务拿到简历时一定问"帮我排个序""有什么区别"——这是必答题，不是加分项。

---

### 第三部分：推荐摘要（可直接转发业务）

**独立章节，格式统一，复制即发。** 不带薪资、不带隐私（电话邮箱不出现）。

**按工作室分组**（和第二部分的组织保持一致）——业务方拿到转发时按归属团队拆分发。

```markdown
---

# 第{n}部分 · 推荐摘要（可直接转发业务）

> 本章节为复制即发版，不含薪资/电话/邮箱等隐私。按工作室分组。

## {工作室1}

### {姓名} · {岗位名}
**推荐理由**：{2-3句：经验年限、相关项目角色、量化产出、技术栈/风格对口度}

**风险提示**：{1句。没有则整段省略}

**建议面试重点**：{1-2句，把"简历解不开的疑问"转化为"面试该问什么"}

## {工作室2}
...
```

### 第四部分：待处理 Action 清单（待定专属）

**表格必须有「工作室/团队」列**——HR 可以按业务方拆分跟进任务。

```markdown
---

# 第{n}部分 · 你需要做的（待定 Action 清单）

| 姓名 | 工作室/团队 | 岗位 | 待做事项 | 为什么定不了 |
|------|------------|------|---------|-------------|
| 杨江海 | 长青/技术 | Unity客户端 | 电话确认方向迁移意愿 | 11 年但全是网赚/休闲，方向跨度大 |
| 余佳辰 | 长青/美术 | 游戏UI | 看简历原件（图片型 PDF 无法提取） | 文本不可判 |
| ... | ... | ... | ... | ... |
```

**Action 必须具体可执行**：不是"建议复核"（废话），而是"差什么信息、看什么就能定"。

---

### 第五部分：兜底区（需人工看原文件）

```markdown
---

# 第{n}部分 · 需人工看原文件

- **{姓名}**：{issue}（图片型 PDF/扫描件/乱码/空文本），BOSS 标 {年限} {岗位}。
- **{姓名}**：{issue}。

> 需要看原件的请找 Agent 取本地路径。
```

**关键**：发布版（飞书 import）会自动剔除本地路径——飞书读者打不开 `F:/...`，让他们找 Agent 要原件。完整报告 md 里才保留路径。

## 终端展示格式

评估完在终端也按总览→详细顺序展示，但**总览表必发**（即使详细分析写文件）：

```
📊 今日评估：{N}人 — 🟢强推{x} 🟡可推{x} ⚪待定{x} 🔴不推{x}

按工作室分布：
- Magnolia：{x}人 ({x}🟢)
- 长青：{x}人 ({x}🟢)
- 迷你世界：{x}人 ({x}🟢)

[总览表]

强推可直接打包发业务：{强推姓名列表}
你需要处理的待定：{待定姓名+Action}
```

## 判定 emoji

| 档位 | emoji | 含义 |
|------|-------|------|
| 强推 | 🟢 | 亮点突出、方向正、硬性达标，优先推给业务 |
| 可推 | 🟡 | 方向对口、基本达标，值得安排面试 |
| 待定 | ⚪ | 有不确定区，需 HR/业务 复核或补信息再定 |
| 不推 | 🔴 | 有明确硬伤（方向不对口等），不建议推 |
| 已评估 | — | 历史已评估过（如候选人补发作品集），本次不重复评 |

## 岗位排序规则（重要）

**岗位在工作室/团队下的排序，按强推人数优先**：

1. 强推人数多 → 少
2. 同强推数，按可推人数多 → 少
3. 同可推数，按岗位总人数多 → 少
4. 全相同时，按岗位名字母/拼音顺序

**为什么**：让最有价值的岗位排在前面，HR 扫到第一眼就是强推最多的岗位。避免"3 🟢 的岗被排在 1 ⚪ 的岗后面"的反直觉情况。

**示例**（长青美术端）：
```
- 游戏地编（1🟢） → 3D动作（1🟢） → 3D场景（1🟢） → 3D角色（2🟡，无强推） → 游戏UI（1⚪）
```
同强推数（1🟢）的地编/动作/场景排前面，无强推的 3D角色/UI 排后面。

## 特殊情况处理

### 换岗（候选人投错岗位后改投）
- 文件挪到正确岗位目录
- 在正确岗位章节正常评估
- 总览表的「一句话理由」里标注"（换岗修正）"
- 在岗位小节开头用 `>` blockquote 说明换岗情况

```markdown
#### 向兴艳 🟢强推（换岗修正）
**关键发现**：7-20 第一次投 3D 角色设计师是错投——简历开头就写"资深三维动漫设计师"...
```

### 岗位调整（评估后用户判断更合适别的岗位）
- 文件挪到新岗位目录
- manifest 同步更新 target_dir/filename/path/job_name
- **新岗位章节**正常评估
- **原岗位章节**保留但只剩其他候选人
- 总览表「一句话理由」标注"（岗位调整）"
- 总览后单独 blockquote 说明调整原因

```markdown
> 黄雷原归"海外游戏数据产品经理"岗，用户判断更合适 AI UGC 产品经理岗，已挪岗（详见 Magnolia · AI 产品经理章节）。
```

### 已评估候选人补发材料（作品集/补充简历）
- 文件归档到原有岗位目录（不要重复创建 7.XX_N份）
- 在岗位小节加一行简短说明，不重复评估

```markdown
#### 雷曈煦 —（7-20 已评估为强推）
7-20 已评估为强推并归档到 `7.20_3份/强推/`。7-22 候选人补发 919MB 作品集 zip，已归档到同一目录补充作品，不重复评估。
```

### BOSS 投递标题与简历标题冲突
**不直接判死，落待定**。按评估要点"外部信号和简历事实打架 → 标存疑"。

```markdown
#### 龚礼顺 ⚪待定（图片型简历+岗位冲突）
简历是单张 PNG 图片（5.9MB），文件名"龚礼顺_**场景地编**设计师_11年.png"——候选人自己标题是**场景地编**，但 BOSS 投递时选了"3D角色设计师"。

**Action**：① 先看 PNG 原件确认是 3D 角色作品还是场景地编作品；② 与候选人电话确认实际意向岗位。
```

### 文件名冲突（同岗位跨档位子目录）
**归档命名规范**：`{候选人}_{岗位}_{年限}[_附加说明].pdf`。同岗位同候选人有多份材料时，用 `_附加说明` 区分（如 `_作品集`、`_补充作品链接`、`_二次投递`）。

## 分发（评估后必做）

把简历按判定 `mv` 进日期目录下的档位子文件夹：

```
已收集简历/{M.DD}_{N}份/
├── 强推/           ← 可直接打包发业务
├── 可推/
└── 待定·不推/      ← 兜底区文本异常的也放这，标注"需人工看原件"
```

**分发后跑 `verify_archive.py` 确认份数没丢**。告诉用户各档人数。

**跨岗位挪动**（如黄雷从海外数据挪到 AI 产品经理）：
- 源岗位的 7.XX_N份 下的档位子目录如果空了，**删空目录**（`rmdir`）保持干净
- 目标岗位如果已有 7.XX_N份，直接挪进去；没有则创建
- 挪动后文件名按新岗位重命名（`{候选人}_{新岗位名}_{年限}.pdf`）

## 阶段 7：发布飞书文档（分发后必做）

> 报告躺在 notes/ 里不算完成——只有到达 HR 屏幕才算闭环。分发完**自动**进入阶段 7，不等用户问。

**3 步**：

1. **派生发布版**：从 `notes/简历评估_{M.DD}.md` 派生 `notes/_发布版_简历评估_{M.DD}.md`，剔除本地路径 + 「需人工看原文件」整节（只留候选人 issue，不留路径）+ 归档说明整节
2. **导入飞书 Docx**：`lark-cli drive +import --file "./_发布版_简历评估_{M.DD}.md" --type docx --name "简历评估 {M.DD} · {N}人"`（不传 `--folder-token` = 云空间根目录）
3. **发链接**：`lark-cli im +messages-send --user-id YOUR_OPEN_ID --text "{url}"`（纯 URL 单独一条消息，飞书自动渲染卡片）

**报告结构有重大调整（挪岗/换岗/重排）时**，飞书文档标题加备注：
```
简历评估 7.21 · 19人（结构重排版·按工作室分组）
简历评估 7.21 · 19人（更新版·黄雷挪岗）
```

具体命令模板、鉴权检查、返回字段、失败兜底见 [`publish-lark-doc.md`](publish-lark-doc.md)。

**终端最后一行必须打印飞书 url + 本地 md 路径**，便于用户兜底访问。

## 反模式

- **不要用扁平岗位列表** — 扁平排列让 HR 还要手动按业务方归类，效率低。必须按工作室/团队分组。
- **不要总览表缺「工作室/团队」列** — 让 HR 第一眼能按归属团队拆分发。
- **不要把强推少的岗位排在强推多的前面** — 按"强推人数优先"排序，最高价值的岗位要靠前。
- **不要自写脚本封装 lark-cli** — 主会话直接调命令即可。
- **不要评估完不分发** — 第四部分必做，用户要的是"能直接打包发业务"的档位文件夹。
- **不要跳过阶段 7** — 评估完不发飞书=没完成。
- **不要碰薪资** — BOSS 收简历时已按薪酬期望筛过。
- **不要平铺式输出** — 总览表是第一屏，不是按收到顺序逐个罗列。
- **不要同岗位多人无对比** — 业务一定问"帮我排个序""有什么区别"，必须答。
- **不要待定判据模糊** — "建议复核"是废话，必须写"差什么信息、看什么就能定"。
- **不要把 Action 清单的「工作室/团队」列漏掉** — HR 要按业务方拆任务跟进。
