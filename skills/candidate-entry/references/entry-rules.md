# 录入铁律（细节）

> 执行路径细节，按需展开。

#### 录入铁律

- **岗位准入闸门**：录入目标岗必须「我创建 + 开放中(active_status=1)」，`_hire.py` 内置 `job_filter_ok()` 自动校验。暂停/已关闭的岗飞书删不掉，靠准入过滤而非手工避让。
- **job_code 自己查，别问用户**：`python notes/_hire.py --jobs 关键词`；`--by-name` 的 `--job` 直接传岗位关键词（脚本自动解析成 code 并校验）。**绝不手撸 jobs API。**
- **人才索引预热**：预检同人性比对数据源 `notes/_talents_cache.json`（TTL 24h）。缓存 miss 时录入会 fork 后台构建不阻塞（见下方「零翻页铁律」）；录单人无同名歧义时可加 `--force "姓名=new"` 跳过预热提速。
- **岗位名匹配放宽**：简历文件名/口头岗位名 ≠ 飞书岗位全名（"游戏运营"实际叫「游戏内容运营」）。`--jobs 关键词` 只命中实习/校招岗或查无结果时，用宽关键词重查（去掉岗位名后段），从输出挑「全职·社招」的 job_code 传给 `--job <code>`，不停下来反问用户。同名岗（全职+实习并存）直接传 job_code 避开歧义。
- **多人异岗禁止共用一个 `--job`**：`--by-name` 只适合同岗批量，岗位不同必须逐个/拆开跑。跑之前先确认每人岗位。
- **判断"录错岗"先实查 applications**：建投递返回 `exists`（1002206）= 正确岗位投递早存在，不是录错。先 `applications?talent_id=` 实况确认，再动手。
- **闸门不过（🔴 STOP）不许继续**——talent 误关联/投递缺失/投错岗位都是真问题。
- **Document AI 解析 → combined_create 一次写全**，不要先 create 再 update，不要传附件指望自动解析。
- **解析质量防线**（已固化 `_hire.py`，无需手动）：① 姓名尾巴粘连——输入姓名（用户指令/文件名）是 Document AI 解析名的严格前缀且只多 ≤2 字尾时，自动采用输入名并打告警；修正存量档案名用 `hire_combined_update`（birthday 传毫秒时间戳**字符串**）。② 薪酬字样告警——命中「期望薪资/年薪」等关键词只提醒归档侧漏脱敏，不阻断录入。③ 查 talent 档案用 `hire_get_talent()` 封装（name 在 `data.talent.basic_info` 嵌套层），不裸调 api。
- **附件选择铁律**：上传附件必须是**简历文件本体（pdf/docx/doc）**——zip 走三级级联①自动提取，rar 需人工先解压再录；**禁止整包上传**（面试官无法预览；投递主简历一旦绑上压缩包，无 API 换绑、terminate 重建会毁已排面试）。**美术/UIUE 岗作品集 PDF/PPT(PPTX) 可传**（走 `notes/_upload_works.py`）；mp4/图片/压缩包一律不传。闸门已固化在 `_lark_shared.upload_attachment_with_name`（全部 ATS 上传唯一收口），传压缩包/其他格式直接报错。候选人通过邀约链接自助上传的附件不受闸门控制——只能话术引导（"请上传简历 PDF/Word，作品集 PDF/PPT 可一并传，其他格式不用传"），传错了事后解包补传简历挂档案。
- **talent_id 是对账主键**：一切跨数据源匹配用 talent_id（不用姓名，治同名错配）。
- **同人性三层规则**：一个真人只允许一个 talent 档案；档案下可挂**多份简历**（新版/岗位定制版并存，旧简历留档）；每次投递绑各自该看的简历版本。"重复录入"bug 的唯一形态 = 档案分裂（同人两个 talent），不是简历变多。
- **同人性预检闸门**（`_hire.py` 已内置）：combined_create 的服务端去重只按手机/邮箱**精确**匹配，换号/缺号/海外号必分裂——预检（`_lark_shared.find_existing_talent`）三分支：无同名→新建；同名+手机尾4或邮箱命中→**自动复用**老档（新简历挂档案、经历/教育保留）；同名但联系方式对不上→**🔴 歧义拦截**，按报错提示加 `--force "姓名=<档案id>"`（同一人换号）或 `--force "姓名=new"`（同名不同人）重跑。
- **预检零翻页铁律**：预检索引**只读缓存**（毫秒级）；缓存 miss → fail-open 放行（服务端精确匹配兜底 + 在途同名提醒）+ fork 后台构建（`_refresh_talents_index.py` 增量优先；锁 `_talents_build.lock` 防并发）。**任何"录入时在线拉全量/翻页等待"的设计都是错的**，宁可降级不可阻塞。
- **重复录入安全（投递级）**：同候选人重投同岗返回 `1002206 same application exist`，脚本识别为"跳过"（⏭️）不当错——但只在 talent_id 相同时触发，防不了档案分裂（分裂由预检闸门防）。
- **存量 talent 旧简历**：录入复用存量 talent 时，`_hire.py` 已内联自动处理——新附件没挂上会自动补挂（combined_create 复用老档不挂新附件是已知 API 行为）；新投递绑旧附件会自动 terminate+重建换绑（仅限初筛阶段，历史投递只告警不自动 swap 以免丢阶段）。**新旧附件判断按文件名，不比 ID**（上传记录 id 与落档后飞书重新生成的档案附件 id 永不相等）。档案里残留的历史旧简历**保留不删**（成长轨迹参考），只记入 result.stale_attachments 供对账。
- **同名岗位区分**：`--jobs 关键词` 输出已带「招聘类型·流程 | 部门」，同名岗靠此区分。
- 排错细节（字段映射/两套附件 ID 体系的前因后果/swap 手动流程）见 [`notes/hire_record.md`](../../../../../miniwanob/notes/hire_record.md)，日常录入不需要看。
