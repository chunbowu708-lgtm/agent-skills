# 决策记录（规则为什么是这样）

> 维护者参考，不是执行路径。Agent 日常执行只看 SKILL.md。本文件记录每条规则背后的设计约束，供修改/审查时理解决策依据。
>
> 仅记结论性约束（什么/为什么不），不含时间戳、案例叙事。历史沿革见 CHANGELOG。

---

## 录入是原子操作（一条命令完成）

录入 = 录人才 → 建投递 → 三段校验，全部内联进 `_hire.py`，一条命令自动串完。track/verify 改为转发器（逻辑在 `_hire.py`），单独调用仅调试用。
- 约束：可确定的流程交给脚本，不让 AI 临时编排多步工序。

## 岗位准入闸门：必须「我创建 + 开放中」

录入目标岗必须同时满足「我创建 + active_status=1」。`_hire.py` 内置 `job_filter_ok()` 自动校验，即使直接传编号也会校验状态+归属。
- 约束：飞书招聘里暂停/已关闭的岗删不掉（产品限制），只能靠准入过滤而非手工避让。永远用岗位关键词让脚本自动选，不手撸 jobs API。

## 存量 talent 旧简历残留风险

录入复用存量 talent（邮箱/手机命中已有 talent）时，旧简历附件还挂在档案上，投递会自动挂旧附件（可能含过时信息或薪酬）。
- `_hire.py` 录入后自动检测旧附件，有则告警。
- 飞书 API 不支持删旧附件（无 delete 接口；combined_update 只追加不替换主附件）→ 必须提示用户去飞书招聘后台手动删。
- 投递绑旧附件时：`swap_resume.py` 做 terminate 旧投递 + 重建（飞书自动绑最新上传附件），仅限早期阶段。

## 淘汰接口：terminate 是唯一正确路径

飞书招聘的淘汰不是 transfer_stage（job_processes 流程里只有 type 1-7 正常阶段，无淘汰阶段），也不是 PUT /applications/:id 改字段（该接口 404）。
- 唯一正确接口：`POST /hire/v1/applications/:id/terminate`，请求体 `{"termination_type":<int>}`，调后 active_status 变 2。
- 接口完整契约在 lark-hire skill，本条只记"为什么是 terminate 而非其他"。

## 录入链路对归档形态的合同：定位即转换

归档库合法存在 zip 整包（美术岗简历+作品）。录入对 zip 的处理：定位侧（find_resume_by_name）命中即自动提取简历本体落 zip 同目录（幂等，提取后与 zip 并存，多匹配取最新即本体），上传走本体，zip 保留。
- 约束：同一事实在定位/解析/上传三处的认知必须一致——闸门拦住错误却没给正确路径自动化，人工被迫补位解压。rar 不自动提取（zipfile 不支持），人工先解。

## 解析质量防线：输入名 > 服务端解析名

Document AI 的姓名解析可能粘连相邻字段（竖排「性别」拆行版式），是服务端行为不可本地修。录入以用户输入/文件名姓名为权威：解析名是输入名的严格前缀且只多 ≤2 字尾时自动采用输入名。
- 薪酬告警不阻断：上传 ATS 要完整简历，脱敏责任在 collect 管线，录入侧只提醒归档侧漏脱敏（存量 zip/手动归档文件没走过 collect 管线，此处是兜底）。
